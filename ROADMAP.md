## 1. Безопасность (P0)

Главный вывод: **сервер сейчас не авторизует никого**. `checkAuth` проверяет
только, что JWT подписан известным секретом, а сам секрет — публичная строка.
Всё остальное — следствия.

### 1.1. Захардкоженный секрет JWT

`controllers/UserController.js:26,70`, `controllers/StudentContoroller.js:26,70`,
`utils/checkAuth.js:8` — везде литерал `"secret123"`.

Секрет лежит в открытом репозитории, значит **любой человек может выписать себе
валидный токен от имени любого пользователя**, зная только его `_id` (а `_id`
раздаёт `GET /students` без авторизации).

**Что сделать**

- Вынести в `JWT_SECRET` из окружения, падать на старте при отсутствии переменной.
- Перейти на пару access (15 мин) + refresh (30 дней) вместо одного 30-дневного токена.
- Класть в payload `sub`, `role`, `jti`; хранить refresh-токены с возможностью отзыва.
- Добавить logout и инвалидацию всех сессий при смене пароля.

### 1.2. Нет ролевой модели и проверки владельца

| Проблема | Последствие |
|---|---|
| `checkAuth` не различает `User` и `Student` | Токен ученика подходит к учительским эндпоинтам |
| Нет поля `role` в модели `User` | Админ от учителя на сервере неотличим |
| `permission` не проверяется при выставлении оценки | Учитель может поставить оценку по чужому предмету и чужому классу |
| Нет проверки владельца ресурса | Ученик может запросить оценки любого другого ученика по `studentId` в URL |

**Что сделать**

- Добавить `role: 'student' | 'teacher' | 'admin'` и класть роль в токен.
- Middleware `requireRole(...roles)` и `requireSelfOrAdmin`.
- В `MarkController.createMark` и `KtpController.createKtp` — проверять, что
  `req.user.permission` содержит связку «предмет + класс» из тела запроса.
- В выборках оценок ученика — брать `studentId` из токена, а не из URL, если роль `student`.

### 1.3. Публичные эндпоинты, которые не должны быть публичными

Без токена сейчас доступны, среди прочего:

```
DELETE /delete/teacher/:id      → удалить любого учителя
DELETE /student/:id             → удалить любого ученика
PUT    /teacher/:id             → выдать себе любые permission
POST   /marks                   → выставить любую оценку кому угодно
DELETE /ktp/:id                 → удалить план урока вместе со всеми оценками
POST   /class, /subject         → создать класс/предмет
GET    /students, /teacher      → выгрузить всю базу пользователей
```

**Что сделать:** по умолчанию закрыть всё, открывать точечно. Практически:
навесить `checkAuth` глобально на роутеры и вынести в белый список только
`/auth/login`, `/auth/register*`, `/health`, `/docs`.

### 1.4. Утечка хэшей паролей

`UserController.getAllTeacher` и `StudentContoroller.getAllStudents` делают
`find()` и отдают документы целиком — вместе с `passwordHash`.

**Что сделать**

- `select('-passwordHash')` во всех выборках, а лучше — `passwordHash: { select: false }`
  на уровне схемы, чтобы забыть было невозможно.
- Ввести DTO/сериализаторы: контроллер отдаёт не документ Mongoose, а явно
  собранный объект ответа.

### 1.5. IDOR в смене пароля

`UserController.js:122` и `StudentContoroller.js:111` берут `userId` из
`req.params._id`, игнорируя `req.userId` из токена. Плюс результат `findById`
не проверяется на `null` — запрос с несуществующим `_id` роняет обработчик в 500.

**Что сделать:** идентификатор пользователя брать только из токена; параметр из
URL убрать вовсе.

### 1.6. Загрузка файлов

`index.js:64` — имя файла берётся из `file.originalname` как есть.

- Path traversal: имя вида `../../index.js` пишет за пределы `uploads/`.
- Перезапись чужих файлов при совпадении имён.
- Нет ограничения размера и типа — можно залить что угодно и любого объёма.
- Файлы раздаются статикой из `/uploads` — залитый HTML/SVG выполнится в браузере
  пользователя (stored XSS).

**Что сделать**

- Генерировать имя самому (`crypto.randomUUID()` + расширение из белого списка).
- `limits: { fileSize: 5 * 1024 * 1024 }`, проверка MIME **и** магических байтов.
- Отдавать с `Content-Disposition: attachment` или вынести в S3-совместимое
  хранилище (см. [7.3](#73-хранилище-файлов)).

### 1.7. Telegram: чужие уведомления и инъекция в URL

- `POST /marks/:chat_id/:message` — `chat_id` и текст приходят **от клиента**.
  Любой может слать произвольные сообщения в произвольные чаты от имени вашего
  бота. `chat_id` обязан браться из `Student.telegram_id` по `markStudent`.
- Параметры подставляются в URL без кодирования — сообщение с `&` или `#`
  ломает запрос и позволяет подмешать параметры Telegram API.
- Привязка через `getUpdates` по `username` (`TelegramController.js`) —
  ненадёжна и угоняема: достаточно знать чужой `@username` и успеть вызвать
  эндпоинт, пока апдейт лежит в очереди.

**Что сделать**

- Привязка через одноразовый код: пользователь получает код в кабинете и
  отправляет боту `/link <код>` — сервер связывает `chat_id` с аккаунтом.
- Уведомления — только в чат, привязанный к самому ученику.
- Отправка через `axios.post(url, { chat_id, text })` телом, а не query-строкой.
- Вынести уведомления в очередь (см. [5.4](#54-фоновые-задачи)) — сейчас падение
  Telegram API тормозит HTTP-ответ учителю.

### 1.8. Базовая гигиена HTTP

| Чего нет | Что добавить |
|---|---|
| Заголовков безопасности | `helmet()` |
| Ограничения источников | `cors({ origin: [...из ENV] })` вместо `cors()` в `index.js:70` |
| Rate limiting | `express-rate-limit`, отдельно жёсткий лимит на `/auth/*` |
| Защиты от перебора | Блокировка аккаунта после N неудачных входов, экспоненциальная задержка |
| Лимита размера тела | `express.json({ limit: '100kb' })` |
| Требований к паролю | Сейчас минимум 5 символов; поднять до 8+ и проверять по списку утёкших (`zxcvbn` / HIBP k-anonymity) |
| Защиты от NoSQL-инъекций | `express-mongo-sanitize` + приведение типов в валидации |

## 3. Доменная модель и бизнес-логика (P1)

Сейчас модель — плоская: все связи это `String` с `_id` внутри, `Predmet.classes`
и `User.permission` — нетипизированные `Array`.

### 3.1. Нормализация схем

- Заменить строковые идентификаторы на `mongoose.Schema.Types.ObjectId` + `ref`,
  использовать `populate` вместо ручной склейки на клиенте.
- Переименовать поля в понятные: `Mark.markDate` на самом деле хранит **id КТП**,
  а не дату — это ловушка для любого, кто откроет код (включая будущего вас).
- `Predmet.classes` и `User.permission` описать вложенными схемами со строгими
  полями вместо `type: Array`.
- Ввести `Schedule`/`Lesson` как отдельную сущность, если понадобится расписание.

### 3.2. Индексы и инварианты на уровне БД

| Индекс | Зачем |
|---|---|
| `Mark: { markStudent, markDate } unique` | Одна оценка на ученика за урок — сейчас дубли создаются свободно |
| `Ktp: { ktpPredmet, ktpClass, ktpDate } unique` | Заменяет ручную проверку дублей из [2.8](#2-баги-и-корректность-p0p1) |
| `Ktp: { ktpPredmet, ktpClass, ktpPeriod, ktpSorSoch }` partial unique для `soch` | Гарантия «один СОЧ в четверти» на уровне БД, а не в коде |
| `Student: { classId }`, `Mark: { markStudent, markPredmet, markPeriod }` | Основные выборки идут по этим полям |

### 3.3. Правила предметной области, которые стоит формализовать

Сейчас в коде живут два правила (дубль КТП и один СОЧ в четверти), остальное не
проверяется. Кандидаты на явные доменные проверки:

- `markValue <= markMaxValue` и `markValue >= 0` — сейчас можно поставить 500 из 30.
- `markMaxValue` должен совпадать с `ktpMaxValue` соответствующего КТП, а не приходить от клиента.
- Оценку нельзя ставить за урок в будущем.
- Нельзя ставить оценку ученику не из того класса, для которого создан КТП.
- Если `markFalse === true` (отсутствовал), `markValue` должен быть пустым, а не `0`.
- КТП удаляется вместе с оценками — сейчас это делается двумя операциями без
  транзакции; нужна транзакция или soft-delete.
- Четверть должна закрываться: после закрытия оценки не редактируются без роли админа.

### 3.4. Расчёт итоговой оценки

Сейчас сервер отдаёт сырые списки оценок, а итог считает фронтенд. Это ключевая
бизнес-логика системы, и её место — на сервере:

- Эндпоинт `GET /api/students/:id/grades/summary?period=1` возвращает по каждому
  предмету: процент за СОР, процент за СОЧ, итоговый балл и оценку по шкале.
- Веса (СОР/СОЧ/формативное) вынести в конфигурацию, а не хардкодить.
- Покрыть расчёт unit-тестами — это то место, где ошибка стоит дороже всего.

### 3.5. Аудит

Оценка — юридически значимая запись. Нужен журнал: кто, когда, какое значение
поставил и на какое изменил. Отдельная коллекция `AuditLog` + soft-delete вместо
физического удаления оценок.

| A2 | Как **ученик**, я хочу входить по email и паролю, чтобы видеть свои оценки | ✅ |

## 5. Архитектура и стек 2026 (P1–P2)

### 5.1. Слои

Сейчас: `index.js` (50+ роутов) → контроллер (валидация + бизнес-логика + запросы к БД).
Цель:

```
src/
├── app.ts                  # сборка Express-приложения (без listen)
├── server.ts               # bootstrap, graceful shutdown
├── config/                 # схема ENV с валидацией через zod, падение на старте
├── modules/
│   ├── auth/               # routes → controller → service → repository
│   ├── users/
│   ├── students/
│   ├── classes/
│   ├── subjects/
│   ├── lessons/            # бывший ktp
│   ├── grades/             # бывший marks + расчёт итогов
│   └── notifications/      # telegram
├── middleware/             # auth, rbac, errorHandler, requestId, rateLimit
├── domain/                 # чистые функции: расчёт итоговой оценки, правила
└── shared/                 # logger, errors, dto
```

Ключевое: **бизнес-правила — чистые функции в `domain/`**, не зависящие от Express
и Mongoose. Их можно тестировать без базы, и именно они переживут любую смену стека.

### 5.2. Язык и типы

**TypeScript — самое ценное вложение в этот проект.** Половина багов из раздела 2
(`res.res()`, `req.params.studentId` вместо `userId`, `markDate` как id) не
существовала бы при статической типизации.

Порядок миграции без остановки разработки:

1. `allowJs: true`, `checkJs: false` — TS собирает существующий JS.
2. Переименовать файлы в `.ts` по одному модулю, начиная с `utils/` и `models/`.
3. Включить `strict: true` после миграции последнего файла.

### 5.3. Библиотеки: чем заменить

| Сейчас | 2026 | Почему |
|---|---|---|
| Express 4 | **Express 5** (стабилен с 2024) или **Fastify** | Express 5: async-обработчики без обёрток, ошибки ловятся сами. Fastify: быстрее, схемы валидации из коробки, OpenAPI генерируется |
| `express-validator` | **zod** | Одна схема на валидацию, типы TS и OpenAPI |
| Mongoose 6 | **Mongoose 8** | Актуальная версия; callback-API уже удалён — потребует правок из [2.7](#2-баги-и-корректность-p0p1) |
| `bcrypt` (нативный) | **argon2** или `bcryptjs` | argon2id — современный стандарт; `bcrypt` требует компиляции и ломает Docker-сборки |
| `jsonwebtoken` 8 | **jose** | Поддерживается, работает в любом рантайме, безопаснее по умолчанию |
| `i18n` (глобальное состояние) | **i18next** или простой словарь + `Accept-Language` | Убирает гонку из [2.10](#2-баги-и-корректность-p0p1) |
| Ручной `swagger/options.js` (2000 строк) | **zod-to-openapi** / `fastify-swagger` | Спека перестаёт расходиться с кодом |
| `node-telegram-bot-api` polling | **grammY** + webhook | Активно поддерживается, TS из коробки, webhook не конфликтует между инстансами |
| `console.log` | **pino** | Структурированные JSON-логи |
| `nodemon` | `node --watch` | Встроено в Node 18+, зависимость не нужна |

> Отдельно: рассмотреть **PostgreSQL + Prisma/Drizzle** вместо MongoDB. Данные
> здесь строго реляционные (ученик → класс → предмет → урок → оценка), а
> отсутствие внешних ключей — прямая причина проблем из раздела 3. Это самая
> дорогая миграция в списке; делать её только после того, как всё остальное
> закрыто, и только если хочется получить опыт с SQL — на текущих объёмах
> MongoDB работать не мешает.

### 5.4. Фоновые задачи

Telegram-уведомления сейчас отправляются синхронно внутри HTTP-запроса
(причём `axios.post` даже без `await` — ошибка отправки теряется молча).

Нужна очередь: **BullMQ + Redis** либо, для pet-проекта, простая таблица `outbox`
с воркером. Даёт ретраи, идемпотентность и отвязку от времени ответа Telegram.

### 5.5. API-контракт

- Префикс `/api/v1` — сейчас версии нет вообще.
- Единый формат ошибки: `{ error: { code, message, details } }` вместо
  трёх разных форматов (`{message}`, массив от `express-validator`, голая строка).
- REST-именование: `/predmet` → `/api/v1/subjects`, `/ktps/my/...` →
  `/api/v1/lessons?subjectId=&classId=`, `/delete/teacher/:id` →
  `DELETE /api/v1/teachers/:id`. Фильтры — в query, а не в пути.
- Пагинация и сортировка на всех списках (`GET /marksall` вернёт всю базу оценок школы).
- Идемпотентность для операций записи.

## 7. Эксплуатация и наблюдаемость (P2)

### 7.1. Docker и окружения

`Dockerfile` (multi-stage, non-root user) + `docker-compose.yml` с MongoDB и Redis.
Один `docker compose up` вместо «поставь Node, заведи Atlas, создай двух ботов».

### 7.2. Конфигурация

Схема окружения на `zod`: приложение падает на старте с внятным сообщением, если
`JWT_SECRET` не задан, а не работает с `"secret123"`.

### 7.3. Хранилище файлов

`multer.diskStorage` пишет на диск инстанса — на Render файлы исчезают при каждом
передеплое. Перейти на S3-совместимое хранилище (Cloudflare R2, MinIO локально) с
загрузкой по presigned URL.

### 7.4. Мониторинг

- `GET /health` (liveness) и `GET /ready` (проверка соединения с MongoDB).
- `pino` + `requestId` в каждой строке лога.
- Sentry для необработанных исключений.
- Graceful shutdown: закрыть HTTP-сервер, дождаться запросов, закрыть Mongoose.

## Что дать себе прочитать перед стартом

Разбор кода 2023 года — не повод его стыдиться. Проект решает настоящую задачу,
в нём есть i18n, документация, интеграция с Telegram и продуманные доменные
правила вроде «один СОЧ в четверти» — для 18 лет и первого большого pet-проекта
это заметно выше среднего. Долг здесь ровно того сорта, который набирается у
всех, кто учится на реальной задаче, а не на туториале.

Порядок работ важнее объёма: сначала этап 0, потом всё остальное.
